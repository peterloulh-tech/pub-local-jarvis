# 本地 AI 游戏弹幕软件产品需求

## 1. 文档目的与状态约定

本文记录基于现有 `pub-local-jarvis` 二次开发的产品目标和已经确认的未来需求。本文是需求基线，不代表所列功能已经实现。

全文使用以下状态约定：

- **当前基线**：已经由现有代码或既有代码库文档确认的能力或限制。
- **首期需求**：计划在首个可交付版本中实现，当前不得视为已完成。
- **后续需求**：首期之后评估或实现，不属于当前能力。
- **待确认**：必须通过模型资料、代码实现或真实硬件测试补充，本文不预设具体结论。

常用术语：

- GPU（图形处理器）：执行模型计算和图形任务的硬件。
- VRAM（显存）：GPU 可直接使用的内存。
- CPU（中央处理器）：承担通用计算任务的硬件。
- Worker（原生工作进程）：负责采集、模型推理和底层任务的独立进程。
- Full-duplex（全双工）：持续接收画面或音频并独立产生响应的交互方式。
- Queue（队列）：按规则保存和依次发送待处理项目的数据结构。
- Checksum（校验值）：用于确认下载文件完整性和身份的哈希值。
- API（应用程序接口）：客户端与服务端或模块之间交换数据的约定。
- UI（用户界面）：用户直接操作和查看的界面。
- Electron（桌面应用框架）：承载控制面板、桌宠和弹幕窗口的桌面运行环境。
- Python（编程语言及后端运行环境）：承载本地 API 和业务编排。
- C++（系统编程语言）：承载原生 Worker、采集和模型运行时适配。
- Named Pipe（命名管道）：Windows 本地进程之间的通信机制。
- DXGI（Windows 桌面复制图形接口）：当前屏幕采集使用的 Windows 图形接口。
- WASAPI（Windows 音频会话接口）：当前系统播放音频采集使用的 Windows 接口。

## 2. 产品定位

### 2.1 目标产品

目标是形成一套面向游戏主播的本地 AI 游戏弹幕软件，核心能力包括：

- 持续识别游戏画面；
- 根据运行模式选择是否同时分析系统游戏音频；
- 自动生成类似真实观众发言的短弹幕；
- 普通游戏场景保持稳定、连续的弹幕输出；
- 高光时刻自动增加弹幕数量和发送频率；
- 根据主播电脑性能选择不同大小和能力的本地模型；
- 优先保证可运行、可恢复和长时间稳定，再持续提高弹幕质量；
- 支持未来的商业联网授权和单设备绑定。

### 2.2 当前基线与未来目标

当前基线包括 Electron 桌面端、Python 后端、C++ Worker、本地 MiniCPM-o 4.5 推理、结构化感知、游戏方案、弹幕窗口、桌宠和普通助手逻辑。当前 `feature-forced-game-mode` 分支还实现了本次运行由用户选择的 `assistant`/强制 `game` 两值 `runtimeMode`，但尚待 GitHub Windows 验证和真实 Windows/NVIDIA 实测。当前代码仍存在弹幕序列被新结果覆盖、原生采集失败回传不足、模型管理单一、缺少商业授权等限制。

下列内容均属于未来需求，不得描述成当前已存在功能：

- MiniCPM-V 4.0 和 MiniCPM-V 4.6 的适配；
- 多模型选择、独立下载按钮和完整下载状态机；
- 在当前两值 `runtimeMode` 基础上拆分完整的“专注游戏/画面加音频游戏/普通助手”三种产品模式，以及模型兼容校验；
- 弹幕统一队列 V2；
- 多提示词、权重随机和游戏专项高光；
- 完整暂停/停止状态机和自动恢复；
- 品牌替换与首次启动引导；
- 联网 K 码授权及管理后台；
- 一键导出诊断包。

## 3. 产品优先级原则

产品和技术决策按以下顺序权衡：

1. 程序能够安装、启动、暂停、停止并正确释放资源；
2. 连续运行稳定，故障能够发现、回传和恢复；
3. 模型、运行模式和硬件能力组合明确且可校验；
4. 弹幕生成与发送连续、可控、不丢失；
5. 提升场景判断、高光识别和弹幕质量；
6. 完成品牌、商业授权和规模化交付能力。

### 4.4 选择和下载必须解耦

模型选择与模型下载是两个完全独立的动作。正确流程必须是：

```text
选择模型
→ 显示模型说明、能力、推荐配置和当前下载状态
→ 用户主动点击独立的“下载”按钮
→ 才允许开始下载
```

强制规则：

- 选择或切换模型后绝对不能自动开始下载；
- 不得在模型选择后静默下载；
- 未下载模型允许被查看和选中；
- 未下载、损坏或校验失败的模型不得启动推理；
- 当前选中模型不可用时，启动按钮必须禁用；
- 禁用启动时显示“当前模型尚未下载”或对应损坏、校验失败原因；
- 下载行为必须由清晰、独立、可追溯的用户操作触发。

### 4.5 下载状态与操作

每个模型必须显示以下状态：

- 未下载；
- 等待下载；
- 下载中；
- 已暂停；
- 校验中；
- 可使用；
- 下载失败；
- 文件损坏。

每个模型按当前状态提供适用操作：

- 下载；
- 暂停；
- 继续；
- 取消；
- 重新下载；
- 删除本地模型。

取消和删除必须明确说明是否保留可继续下载的临时文件。删除本地模型不得删除用户设置、游戏方案或授权信息。

### 4.6 模型帮助说明

每个模型旁提供“？”帮助入口，至少说明：

- 推荐电脑配置；
- 模型大小和大致磁盘、内存、VRAM 占用；
- 支持纯画面还是画面加音频；
- 是否支持 Full-duplex；
- 推荐运行模式；
- 大致速度与效果差异；
- 未达到推荐配置时可能出现的性能或稳定性问题。

## 5. 运行模式

### 5.1 当前实现：assistant 与强制 game

当前代码已经实现以下两值运行控制，但仍处于待 Windows 验证状态：

- `assistant`：默认模式，保留现有自动场景识别、桌宠、课程和场景控制弹幕逻辑；
- `game`：用户本次启动明确选择的强制游戏弹幕模式，持续采集画面和系统音频，每轮使用游戏提示词和当前游戏方案，并允许真实 `scene` 为 `game`、`other` 或 `course` 时继续处理合法游戏弹幕候选。

控制优先级必须固定为：

```text
用户选择的 runtimeMode
> 模型输出的 scene
```

含义如下：

- `runtimeMode` 只由用户选择和本次启动参数确定；
- 模型必须继续如实输出 `game`、`other`、`course`，用于识别结果和诊断；
- 模型 `scene` 不得修改 `runtimeMode`；
- 强制 `game` 中，`scene` 不得停止结构化感知、清空合法游戏候选、取消游戏弹幕流程或隐藏弹幕窗口；
- 强制 `game` 中，`screen_idle` 仍可记录和产生状态事件，但不得暂停新的结构化感知调度；任务防重、单任务在途和队列限流仍必须保留；
- `assistant` 继续按原 `scene` 和 `screen_idle` 逻辑运行。

当前强制 `game` 会采集系统音频，Python 也仍按现有 monitoring 流程创建 ambient duplex；因此它不能被描述为下面规划中的“专注游戏模式”已经实现。启动时成功同步游戏方案后只显示一次方案加载提示，`scene` 变化和暂停/恢复不得重复提示。

### 5.2 未来需求：专注游戏模式

首期需求：

- 强制隐藏桌宠；
- 持续读取并分析游戏画面；
- 不读取音频；
- 不启动后台 Full-duplex；
- 只运行结构化感知和弹幕生成；
- 优先降低 VRAM、内存和算力占用；
- MiniCPM-o 与 MiniCPM-V 系列均可使用，但仍需分别验证运行时兼容性。

### 5.3 未来需求：画面加音频游戏模式

首期需求：

- 强制隐藏桌宠；
- 持续读取游戏画面；
- 同时分析系统游戏声音；
- 结合画面和音频生成弹幕；
- 仅允许明确支持音频的模型使用。

若底层实现采用持续流式双上下文，技术文档可以标注“全双工游戏模式”；产品 UI 优先使用“画面加音频游戏模式”，避免用户误解为语音通话或语音播报。

### 5.4 未来产品形态：普通助手模式

首期需求：

- 恢复现有 Jarvis 桌面助手逻辑；
- 显示桌宠；
- 保留普通桌面感知、主动对话和现有 Full-duplex 逻辑；
- 允许用户手动隐藏桌宠。

### 5.5 模型与模式兼容校验

| 模型 | 专注游戏模式 | 画面加音频游戏模式 | 普通助手模式 |
| --- | --- | --- | --- |
| MiniCPM-o 4.5 | 允许 | 允许 | 允许 |
| MiniCPM-V 4.0 | 允许 | 禁用 | 禁用 |
| MiniCPM-V 4.6 | 允许 | 禁用 | 禁用 |

系统必须：

- 在 UI 中禁用明显不兼容的组合；
- 在保存、启动和后端执行前重复校验；
- 不允许通过旧设置、导入文件或直接 API 调用保存不兼容组合；
- 对模型未下载、文件损坏或能力不兼容分别提供明确提示。

## 6. 感知设置

### 6.1 游戏感知间隔

提供以下预设：

- 1 秒；
- 2 秒；
- 3 秒；
- 4 秒；
- 5 秒；
- 自定义。

自定义范围建议为 0.5 秒至 30 秒。最终默认值和范围必须通过不同硬件、模型与游戏实测确认，并保留后续调整能力。

启用音频时，音频分析节奏应与画面感知协调，但允许读取最近一段滚动音频窗口，不要求音频长度机械等于单个画面感知间隔。

帮助文字必须说明：

- 间隔越短，响应越及时；
- 间隔越短，GPU 和 CPU 负载通常越高；
- 间隔越长，弹幕可能滞后或错过短暂事件。

### 7.1 游戏方案

保留现有新增、编辑、选择和删除游戏方案能力。首批内置方案建议包括：

- 永劫无间；
- 英雄联盟；
- PUBG；

- 默认感知间隔；
- 默认弹幕间隔；

内置方案更新不得覆盖用户已经修改的提示词。内置默认值、用户覆盖值和版本迁移状态必须分开保存。

### 7.2 多套提示词

每个游戏方案允许创建多套提示词，例如：

- 夸赞；
- 调侃；
- 吐槽；
- 御姐；
- 甜美；
- 撒娇；
- 电竞老哥；
- 理性观众。

每套提示词包含：

- 名称；
- 正文；
- 是否启用；
- 选择权重；
- 创建时间；
- 修改时间。

支持：

- 等概率随机；
- 按权重随机；
- 预览测试；

- 恢复默认；
- 导入；

提示词只能影响表达风格、称呼、语气和关注方向，不得把提示词中的虚构内容当作真实画面事实。

## 8. 弹幕生成与显示

### 8.1 生成和发送解耦

模型负责生成候选弹幕，统一发送调度器负责按时间和优先级显示。新模型结果不得直接控制多个独立定时任务，也不得因为新结果到达就无条件丢弃旧结果。

弹幕发送间隔提供：

- 1 秒；
- 2 秒；
- 3 秒；
- 4 秒；
- 5 秒；
- 自定义。

例如一组 3 条弹幕、间隔 2 秒：

- 第 1 条立即发送；
- 第 2 条在 2 秒后发送；
- 第 3 条在 4 秒后发送。

### 8.2 字数规则

- 最短字数可配置；
- 最长字数可配置；
- 建议默认 4 至 16 个中文字符；
- 系统最长建议为 30 个中文字符；
- 不允许只有标点；
- 超长内容应在标点、短语或语义边界缩短，不得从词语中间粗暴截断。

### 8.3 显示范围

- 横向范围对应屏幕左右坐标；
- 纵向范围对应屏幕上下坐标；
- 调整时支持实时预览；
- 范围值必须适配不同分辨率、缩放比例和多显示器。

后续可以增加：

- 字体大小；
- 透明度；
- 移动速度；
- 同屏数量；
- 屏幕边距；
- 是否允许重叠。

### 8.4 显示内容

移除当前弹幕前方蓝色“JARVIS”文字。最终只显示弹幕正文，不显示品牌、头像、图标、前缀或冒号。

## 9. 弹幕队列 V2

弹幕队列 V2 属于未来需求，用于修复当前新有效弹幕组取消旧组剩余发送任务的问题。

### 9.1 队列原则

- 新弹幕组不得直接取消旧弹幕组；
- 已生成弹幕进入统一发送 Queue；
- 新结果继续补充 Queue；
- 最多保留 5 组待发送弹幕；
- 全局只有一个发送调度器；
- “最多 5 组”指已生成或待发送的弹幕组，不代表允许同时执行 5 次模型推理。

### 9.2 推理并发

- 同一时间最多 1 个模型推理任务；
- 模型繁忙时最多保留 1 个最新待分析画面；
- 中间过时画面允许丢弃；
- 不允许 5 次 GPU 推理并发；
- 推理任务、待分析画面和待发送弹幕必须使用不同状态和指标。

### 9.3 队列淘汰和有效期

队列满时依次优先清理：

1. 已过期弹幕；
2. 最早的普通弹幕；
3. 高重复弹幕。

普通弹幕初始建议有效期约 12 秒；高光弹幕可以稍长。两者均为可调整默认值，必须根据真实游戏节奏和显示效果实测，不能写死为永久规则。

## 10. 稳定性和自动恢复

### 10.1 优先问题

- `game` 和 `other` 场景反复切换；
- 验证强制游戏模式的一次性方案提示在Windows长时间运行、暂停/恢复和scene变化中不回归；
- 弹幕或感知运行数分钟后停止；
- 推理任务永久忙碌；
- Full-duplex 上下文重建失败；
- 屏幕采集冻结；
- 音频采集冻结；
- Worker 崩溃后无法恢复；
- 采集启动失败但界面显示成功。

### 10.2 恢复机制

需要设计并实现：

- 推理超时；
- Worker 心跳；
- Worker 自动恢复；
- 上下文重建失败恢复；
- 屏幕和音频采集失败状态回传；
- 诊断日志；
- 运行状态监控；
- 对自动恢复次数、间隔和最终失败状态的限制。

所有超时、重试次数和恢复间隔必须先作为可调整默认值，通过实测收敛，不得直接写成永远固定的最终值。

## 11. 暂停、停止和运行状态

### 11.1 暂停

- 停止获取新画面和音频；
- 停止生成新弹幕；
- 保留 Electron 管理的 Backend、Worker 和已经加载的模型；
- 保留恢复所需的安全状态；
- 恢复时沿现有 Backend/Worker 会话快速继续，不得退化为重新启动或重新加载模型。

暂停期间如何处理已经进入 Queue 的弹幕尚待产品确认，实现前必须明确是保留、丢弃还是恢复后重新检查有效期，不得由单层代码自行决定。

### 11.2 停止

- 停止画面采集；
- 停止音频采集；
- 停止全部推理任务；
- 清空弹幕 Queue；
- 停止 Full-duplex 任务；
- 卸载模型；
- 释放 GPU VRAM；
- 关闭或重置 Worker；
- 恢复到程序刚打开、尚未启动模型的状态。

当前 Electron 基础生命周期已经提供真正停止：仅对 Electron 自己启动并管理的 Backend 执行 `shutdown`、终止自有 Backend/Worker 进程树并关闭相关 WebSocket 连接。停止失败必须恢复操作前状态并显示明确错误，不得假装进入 `idle`；已连接但非 Electron 自有的 Backend 不得被擅自终止。Windows 真实进程树终止、模型资源与 GPU VRAM 释放仍待 Windows/NVIDIA 实机验证。

### 11.3 状态机

运行状态包括：

- 未启动；
- 模型加载中；
- 运行中；
- 已暂停；
- 正在停止；
- 已停止；
- 故障。

UI、Electron 主进程、Python 后端和 Worker 必须对状态含义保持一致。状态切换必须有明确的允许路径、超时和失败结果，不能只更新界面文字。

## 15. 诊断和隐私

### 15.1 诊断包

未来增加导出诊断包能力，允许包含：

- 软件版本；
- 当前运行模式；
- 当前模型；
- 模型下载状态；
- GPU 和 VRAM 信息；
- 分析耗时；
- Queue 长度；
- 场景切换；
- 超时记录；
- Worker 重启记录；
- 最近日志。

诊断包不得包含：

- K 码明文；
- 授权私钥；
- 用户隐私文件；
- 完整麦克风录音。

### 15.2 临时媒体风险

当前结构化感知和 Full-duplex 运行时可能在系统临时目录写入 BMP（位图图像格式）画面或 WAV（波形音频格式）音频文件，正常流程会尝试清理，但异常崩溃时可能残留。后续必须：

- 明确临时目录和文件命名；
- 启动时清理确认属于本程序的陈旧临时文件；
- 停止和退出时执行清理；
- 限制目录权限；
- 不在日志或诊断包中默认打包这些文件；
- 在隐私说明中披露本地临时处理行为。

## 16. 非功能验收原则

- 所有未来功能必须有明确的状态、失败结果和用户提示；
- Windows 原生采集、Named Pipe、CUDA（英伟达并行计算平台）、安装包和真实游戏行为必须在 Windows 验证；
- CUDA、VRAM 释放和 NVIDIA 性能必须在 NVIDIA 实机验证；
- 纯 Mac 测试不能证明上述 Windows 或 GPU 行为；
- 模型与模式兼容必须在 UI、保存、后端和 Worker 边界重复校验；
- 任何宣称“已完成”的阶段必须满足对应验收标准，并列出仍未执行的实机验证。
