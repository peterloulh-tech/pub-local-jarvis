# 本地 AI 游戏弹幕软件开发路线

## 1. 文档说明

本文把已确认的产品需求拆分为第 0 至第 9 阶段。除明确标记为当前基线的文档外，各阶段内容都是未来开发计划，不代表功能已经实现。

术语说明：

- Git branch（Git 分支）：隔离一组相关修改的独立开发线。
- Acceptance criteria（验收标准）：判断阶段是否真正达到目标的可检查条件。
- Smoke test（冒烟测试）：用最小关键流程确认应用能够启动并完成核心动作的检查。
- Named Pipe（命名管道）：Windows 本地进程之间的通信机制。
- CUDA（英伟达并行计算平台）：用于 NVIDIA GPU 加速模型推理的运行环境。
- GPU（图形处理器）、VRAM（显存）、Worker（原生工作进程）和 Queue（队列）的含义见 `PRODUCT_REQUIREMENTS.md`。

## 2. 总体执行原则

- 每个阶段只处理一个主要产品边界，建议使用独立 Git branch；
- 稳定性和生命周期优先于模型数量、弹幕风格和商业界面；
- 修改前必须追踪 UI、持久化、Electron、Python、Worker 和实际效果的完整数据流；
- 模型选择与下载始终是独立动作，选择模型后不得自动下载；
- 同一时间最多执行一个模型推理任务，弹幕 Queue 容量不能解释为推理并发数；
- 超时、心跳、重试、冷却和有效期先使用可调整默认值，再通过实测收敛；
- 无法在 Mac 验证的 Windows、Named Pipe、CUDA、NVIDIA、安装包、全屏窗口和游戏行为必须标记为未实机验证；
- 一个阶段只有在相关自动测试通过、必要实机验收完成或明确列出未验证项后才能交付；
- 阶段分支名称是建议，不强制覆盖团队既有命名规范。

## 3. 阶段依赖关系

```text
第0阶段 开发基线
→ 第1阶段 稳定性修复
→ 第2阶段 运行模式和模型生命周期
→ 第3阶段 模型管理
→ 第4阶段 弹幕引擎 V2
→ 第5阶段 游戏方案和多提示词
→ 第6阶段 高光识别
→ 第7阶段 品牌和商业界面
→ 第8阶段 联网 K 码授权
→ 第9阶段 商业交付测试
```

第 4、5、6 阶段可以在接口稳定后局部并行分析，但写入和集成应保持单一责任分支。第 8 阶段可以提前进行服务端方案设计，但授权门禁必须在模型生命周期稳定后再接入客户端。

## 4. 第 0 阶段：开发基线

### 目标

建立可信的代码、产品、测试和构建基线，让后续修改能够判断是否引入回归。

### 包含任务

- 维护代码库地图；
- 维护功能地图；
- 维护 `AGENTS.md`；
- 保存产品需求；
- 保存开发路线；
- 记录原版 Python、JavaScript、C++、Windows 安装包和真实模型测试基线；
- 区分当前能够在 Mac 执行的轻量检查与必须在 Windows/NVIDIA 执行的验证；
- 记录当前已知缺陷和未验证项。

### 前置依赖

- 当前仓库和许可证文件可读；
- 已确认代码库地图和功能地图；
- 有可用的 Windows 测试环境规划。

### 建议独立分支

- 文档：`docs-product-roadmap`；
- 原版构建和实机基线：`baseline/original-build-test`。

本轮只创建文档，不执行原版构建和测试；构建基线仍属于待完成任务。

### 验收标准

- 代码库地图、功能地图、开发纪律、产品需求和开发路线均入库；
- 当前能力与未来需求有明确标记；
- 现有测试命令、可执行平台和未验证路径有记录；
- 原版构建与测试基线在后续专门任务中记录真实命令、结果和环境；
- 没有因基线阶段修改业务代码。

### 风险等级

**低至中。** 文档风险低；真实模型、原生构建和安装包基线存在较高环境风险。

### Windows/NVIDIA 实机要求

- 文档部分：不需要；
- Windows 原生采集、Named Pipe、安装包和真实游戏基线：必须 Windows；
- CUDA、VRAM 和模型性能基线：必须 NVIDIA。

## 5. 第 1 阶段：稳定性修复

### 目标

消除最影响连续运行的故障，建立可发现、可回传、可恢复的运行基础。

### 包含任务

- 减少 `game` 与 `other` 场景抖动；
- 修复重复显示“已加载游戏方案”；
- 定位感知和弹幕运行数分钟后停止的问题；
- 为推理任务增加可调整超时；
- 为 Worker 增加心跳和受限自动恢复；
- 处理 Full-duplex 上下文重建失败；
- 检测屏幕和音频采集冻结；
- 将 DXGI/WASAPI 启动失败可靠回传到 Python、Electron 和 UI；
- 增加运行状态监控和必要诊断日志；
- 防止自动恢复形成无限重启循环。

### 前置依赖

- 第 0 阶段的原版运行基线；
- 可复现问题的日志或最小场景；
- Windows CPU 和至少一套 NVIDIA 测试环境。

### 建议独立分支

`stability/runtime-recovery`

### 验收标准

- 采集启动失败时 UI 不再显示成功；
- 推理超过配置超时后能够退出忙碌状态；
- Worker 异常退出能被发现并按策略恢复或进入明确故障状态；
- Full-duplex 重建失败不会永久卡死整个程序；
- 场景抖动和重复方案提示有可重复测试；
- 连续运行至少完成本阶段约定的短期稳定性测试，并保存日志；
- 所有重试和超时均可配置，不是不可调整常量。

### 风险等级

**高。** 涉及跨进程状态、原生采集、推理调度和恢复边界。

### Windows/NVIDIA 实机要求

- 必须 Windows 验证采集、Pipe、Worker 崩溃和进程恢复；
- 必须 NVIDIA 验证 CUDA 推理超时、上下文重建和 VRAM 压力；
- Mac 只能验证 Python/JavaScript 纯逻辑和静态代码。

## 6. 第 2 阶段：运行模式和模型生命周期

### 目标

建立三种明确运行模式，以及可预测的启动、暂停、恢复、停止和模型卸载流程。

### 包含任务

- 专注游戏模式；
- 画面加音频游戏模式；
- 普通助手模式；
- 模式与模型能力校验接口；
- 游戏模式强制隐藏桌宠；
- 普通助手模式恢复桌宠并允许手动隐藏；
- 暂停时停止新采集和新推理但保留模型；
- 恢复时快速继续；
- 停止时清空 Queue、停止全部任务并卸载模型；
- 释放 GPU VRAM；
- 关闭或重置 Worker；
- 统一未启动、加载中、运行中、已暂停、正在停止、已停止、故障状态。

### 前置依赖

- 第 1 阶段的可靠故障回传和 Worker 恢复基础；
- 已确认当前 simplex、Full-duplex、采集和模型卸载数据流；
- 初步模型能力描述。

### 建议独立分支

`feature/runtime-modes-lifecycle`

### 验收标准

- 三种模式对画面、音频、Full-duplex 和桌宠的行为符合产品需求；
- 不兼容组合在 UI、保存和后端均被拒绝；
- 暂停不卸载模型，恢复无需完整重新加载；
- 停止后采集、推理、Queue 和 Full-duplex 均结束；
- 停止后模型上下文卸载且 VRAM 明显释放；
- UI、Electron、Python 和 Worker 状态一致；
- 每个非法状态切换返回明确错误。

### 风险等级

**高。** 涉及生命周期、资源释放和跨层状态一致性。

### Windows/NVIDIA 实机要求

- 必须 Windows 验证采集、桌宠、透明窗口、暂停和停止；
- 必须 NVIDIA 验证模型卸载和 VRAM 释放；
- 普通助手 Full-duplex 必须使用真实模型验证。

## 7. 第 3 阶段：模型管理

### 目标

提供可理解、可控制、可校验的多模型管理流程，避免静默下载和不兼容启动。

### 包含任务

- 建立 MiniCPM-o 4.5、MiniCPM-V 4.0、MiniCPM-V 4.6 能力清单；
- 记录量化、文件组件、推荐硬件、下载地址和 Checksum；
- 模型列表和模型选择；
- 独立“下载”按钮；
- 未下载、等待、下载中、暂停、校验、可用、失败、损坏状态；
- 下载、暂停、继续、取消、重新下载和删除；
- 下载中断恢复；
- 文件大小、Checksum 和模型布局校验；
- 模型与运行模式兼容校验；
- 模型帮助说明和推荐配置；
- 未下载或损坏时禁用启动；
- 删除模型时保留用户配置和授权数据。

再次强调：

```text
选择模型 ≠ 下载模型
```

选择或切换模型后不得自动下载，只有用户主动点击独立“下载”按钮后才允许开始下载。

### 前置依赖

- 第 2 阶段的模型生命周期和能力校验接口；
- 每个目标模型的官方文件、许可证和运行时资料；
- 可安全暂停和终止下载的下载组件设计；
- 模型本地目录和迁移策略。

### 建议独立分支

`feature/model-management`

### 验收标准

- 选择任意未下载模型不会产生网络下载；
- 只有点击下载按钮才发生下载请求；
- 关闭并重启程序后下载状态能够正确恢复或重新判定；
- 暂停、继续、取消、损坏、重新下载和删除都有测试；
- Checksum 错误不能进入“可使用”；
- 未下载模型的启动按钮禁用并显示“当前模型尚未下载”；
- 不兼容模式不能保存或启动；
- 三个模型的能力和许可证记录完整，未知数据明确标记待确认。

### 风险等级

**高。** 涉及大文件下载、磁盘状态、模型格式、第三方许可证和多运行时适配。

### Windows/NVIDIA 实机要求

- 下载状态机和 Checksum 纯逻辑可跨平台测试；
- 本地目录、安装版权限和断点恢复必须 Windows 验证；
- 每个模型的加载、速度、VRAM 和推荐配置必须在 NVIDIA 实机验证；
- MiniCPM-V 适配不得仅凭 MiniCPM-o 结果推断。

## 8. 第 4 阶段：弹幕引擎 V2

### 目标

将弹幕生成与发送彻底解耦，形成连续、可控、不会因新结果无条件丢弃旧组的统一 Queue。

### 包含任务

- 新弹幕组不取消旧组；
- 建立统一发送 Queue；
- 最多保存 5 组已生成或待发送弹幕；
- 全局只有一个发送调度器；
- 同一时间最多一个模型推理任务；
- 模型繁忙时只保留一个最新待分析画面；
- 丢弃中间过时画面；
- 普通弹幕和高光弹幕有效期；
- Queue 满时清理过期、最早普通和高重复弹幕；
- 弹幕发送间隔；
- 最短和最长字数；
- 语义边界缩短，避免词中截断；
- 横向、纵向显示范围与实时预览；
- 移除蓝色“JARVIS”前缀，只显示正文；
- 记录 Queue 长度、过期、丢弃和发送原因。

### 前置依赖

- 第 1 阶段的稳定推理和超时机制；
- 第 2 阶段的暂停、停止和场景状态；
- 明确结构化感知候选输出接口。

### 建议独立分支

`feature/barrage-engine-v2`

### 验收标准

- 新组到达后旧组未过期内容仍按规则发送；
- Queue 永远不超过 5 组；
- 推理并发始终不超过 1；
- 繁忙期间最多保留一个最新待分析画面；
- 离开游戏、暂停和停止时按产品规则处理 Queue；
- 3 条、2 秒间隔时发送时间符合 0、2、4 秒；
- 超长内容不会从中文词语中间粗暴截断；
- 弹幕最终只显示正文；
- 不同分辨率和缩放下显示范围可预览且不越界。

### 风险等级

**高。** 涉及异步调度、过期策略、场景切换和视觉表现。

### Windows/NVIDIA 实机要求

- Queue、计时和淘汰规则可跨平台单测；
- 透明置顶、全屏游戏、帧率、显示范围和点击穿透必须 Windows 实测；
- 单推理策略和高负载连续性应在 NVIDIA 实机验证。

## 9. 第 5 阶段：游戏方案和多提示词

### 目标

建立可扩展的游戏方案和多风格提示词系统，同时保护用户修改不被内置更新覆盖。

### 包含任务

- 三角洲行动、永劫无间、英雄联盟、PUBG 和其他游戏内置方案；
- 游戏名称、识别进程、默认提示词和辅助信息；
- 默认感知间隔和弹幕间隔；
- 游戏高光规则入口；
- 内置默认值与用户覆盖值分离；
- 每个方案多套提示词；
- 提示词名称、正文、启用、权重和时间；
- 等概率随机和按权重随机；
- 预览测试；
- 复制和恢复默认；
- 导入和导出；
- 导入格式版本和安全校验。

### 前置依赖

- 第 2 阶段的模式和设置持久化；
- 第 4 阶段稳定的弹幕生成/发送边界；
- 明确提示词只控制风格、不提供画面事实的安全规则。

### 建议独立分支

`feature/game-profiles-prompts`

### 验收标准

- 内置方案升级不会覆盖用户修改；
- 启用提示词按等概率或权重规则选择；
- 禁用提示词不会被使用；
- 导入非法或过期格式时明确拒绝且不破坏现有数据；
- 导出后可以在兼容版本恢复；
- 预览测试不会误启动真实游戏推理或修改正式设置；
- 提示词中的虚构内容不会成为场景或高光事实。

### 风险等级

**中至高。** 数据迁移和 UI 为中风险，提示词影响事实边界时为高风险。

### Windows/NVIDIA 实机要求

- 数据结构、随机和导入导出可跨平台测试；
- 真实游戏识别、提示词服从度和弹幕质量必须 Windows+真实模型；
- 性能验证需要 NVIDIA。

## 10. 第 6 阶段：高光识别

### 目标

建立通用规则与游戏专项规则相结合的高光识别，并安全驱动短时弹幕爆发。

### 包含任务

- 通用击杀、多杀、残血反杀、胜负、稀有物品、撤离、团战和结算识别；
- 画面与音效强度突增特征；
- 英雄联盟专项规则；
- 三角洲行动专项规则；
- 永劫无间专项规则；
- 高光类型、置信度和触发时间记录；
- 高光冷却和重复抑制；
- 短时增加弹幕数量；
- 临时缩短发送间隔；
- 高光结束后恢复普通节奏；
- 对误识别和漏识别建立回放/标注评估方法。

### 前置依赖

- 第 4 阶段的 Queue、优先级和有效期；
- 第 5 阶段的游戏专项配置结构；
- 稳定的画面和可选音频感知；
- 可重复的真实游戏样本和测试标准。

### 建议独立分支

`feature/highlight-detection`

### 验收标准

- 通用和专项规则能区分并记录来源；
- 高光需要达到可调整置信度门槛；
- 同一事件在冷却期内不会连续刷屏；
- 高光弹幕可以优先但不会破坏 Queue 上限和单推理原则；
- 误识别、漏识别、触发延迟和弹幕爆发数量有实测记录；
- 普通场景不会长期保持高光频率。

### 风险等级

**高。** 真实游戏差异大，容易产生误判、刷屏和性能压力。

### Windows/NVIDIA 实机要求

- 必须 Windows 真实游戏测试；
- 音效规则必须验证 WASAPI 系统音频；
- 多模型速度和高光延迟必须 NVIDIA 实测。

## 11. 第 7 阶段：品牌和商业界面

### 目标

完成面向商业交付的品牌展示、引导、帮助和授权入口，同时保护内部兼容标识和许可证义务。

### 包含任务

- 软件名称；
- Logo；
- 安装包名称；
- 托盘名称；
- 快捷方式；
- UI 品牌文字；
- 首次启动引导；
- 模型“？”帮助；
- 许可证入口；
- 隐私和诊断说明；
- 分别梳理展示品牌与内部 `Jarvis`/`AIJarvis`/`JARVIS` 标识；
- 同步评估 `AI Jarvis Pet` 窗口标题与 DXGI 显示器选择；
- 核验安装产物中的 MIT 和第三方声明。

### 前置依赖

- 第 2、3 阶段的模式、模型和启动流程稳定；
- 已确认新品牌名称、Logo 资产和法律使用范围；
- 完整的内部标识清单和许可证清单。

### 建议独立分支

`feature/brand-commercial-ui`

### 验收标准

- 展示名称、Logo、安装包、托盘和快捷方式一致；
- 不进行全仓库批量字符串替换；
- 品牌修改后桌宠显示器捕获仍正确；
- 升级安装不会破坏用户模型、设置和游戏方案；
- 安装目录和关于页面包含所需许可证与声明；
- 首次引导明确解释模型下载需用户主动触发。

### 风险等级

**中至高。** 视觉替换为中风险，安装包、内部标识和原生窗口耦合为高风险。

### Windows/NVIDIA 实机要求

- 必须 Windows 验证安装包、托盘、快捷方式、窗口标题和多显示器捕获；
- 品牌本身通常不要求 NVIDIA，但必须在 NVIDIA 机器回归模型启动和游戏模式。

## 12. 第 8 阶段：联网 K 码授权

### 目标

实现安全、可审计、支持离线宽限和单设备绑定的商业授权系统，并在授权通过后才允许加载模型。

### 包含任务

- 客户端首次激活；
- 30、90、365 天有效期；
- 从首次激活开始计时；
- 一个 K 码同时绑定一台设备；
- 同设备重装恢复；
- 离线宽限期；
- 到期后停止 AI 功能但保留配置；
- 本地授权凭证数字签名；
- 私钥只保留在受控服务端；
- 授权状态机和模型加载门禁；
- 后台生成、查询、禁用、解绑、续期和备注；
- 设备信息最小化；
- 最后在线时间；
- 管理员权限、操作日志和审计；
- 服务不可达、系统时间回拨和凭证损坏处理。

### 前置依赖

- 第 2 阶段可靠的模型启动和停止门禁；
- 第 7 阶段商业 UI 和许可证入口；
- 授权服务、域名、证书、密钥管理和运维方案；
- 已确认隐私政策、用户协议和设备绑定规则；
- 安全评审和威胁分析。

### 建议独立分支

- 客户端：`feature/license-client`；
- 服务端与后台：独立仓库或 `service/license-platform`，不得与模型运行时混杂。

### 验收标准

- 未授权、到期或禁用状态不能加载模型；
- 授权通过才能进入模型加载；
- 一个 K 码不能同时绑定第二台设备；
- 同一设备重装可按规则恢复；
- 离线宽限起止时间可验证且不能无限延长；
- 客户端不包含私钥；
- 本地凭证篡改会被发现；
- 禁用、解绑、续期和后台操作均有审计记录；
- 服务不可达时行为符合产品规则且不破坏用户配置；
- 日志和诊断包不包含 K 码明文或敏感密钥。

### 风险等级

**极高。** 涉及安全、隐私、服务可用性、计费权益和客户端绕过风险。

### Windows/NVIDIA 实机要求

- 授权服务逻辑可在独立测试环境验证；
- 客户端激活、重装、设备变化和本地安全存储必须 Windows 实测；
- NVIDIA 不是授权算法前提，但必须验证授权门禁不会破坏 CPU/CUDA 模型加载和 VRAM 生命周期。

## 13. 第 9 阶段：商业交付测试

### 目标

在不同硬件、模型、模式和异常条件下完成可追溯的发布验收，证明产品具备商业交付所需的稳定性和恢复能力。

### 包含任务

- 不同 GPU、VRAM、内存和 CPU 配置；
- 三个目标模型；
- 三种运行模式；
- 连续运行 4 至 8 小时；
- 下载暂停、继续、中断和取消；
- 模型文件损坏和重新下载；
- 网络断开和恢复；
- 授权到期、禁用、解绑和续期；
- 软件卸载、重装和升级；
- 游戏切换和多显示器；
- 暂停、恢复和停止；
- 模型卸载和 VRAM 释放；
- Worker 崩溃、采集冻结和自动恢复；
- 全屏、透明置顶和点击穿透；
- 诊断包完整性与隐私检查；
- 安装包许可证和第三方声明核验。

### 前置依赖

- 第 1 至第 8 阶段达到各自验收标准；
- 冻结的候选版本、模型清单和授权测试环境；
- 明确的硬件矩阵、游戏矩阵和通过门槛；
- 可复现的安装包和发布记录。

### 建议独立分支

`release/commercial-validation`

该分支只接受发布阻塞问题修复和测试记录，不进行无关重构或新功能扩张。

### 验收标准

- 每个硬件、模型、模式组合有明确通过、失败或不支持结论；
- 至少完成约定数量的 4 至 8 小时连续运行测试；
- 下载、损坏、断网、授权到期和重装场景均有结果；
- 暂停和停止后的采集、任务、Queue、Worker 和 VRAM 状态符合需求；
- 自动恢复不会形成无限循环；
- 诊断包不包含禁止信息；
- 安装包能够安装、升级、卸载并保留应保留的数据；
- 发布产物包含 MIT 和全部必要第三方声明；
- 所有未通过项有责任人、严重级别和发布决策。

### 风险等级

**极高。** 这是发布门禁阶段，任何未覆盖组合都可能成为真实用户故障。

### Windows/NVIDIA 实机要求

- 必须使用真实 Windows 环境；
- 必须覆盖多档 NVIDIA GPU 和 VRAM；
- 应增加至少一套 Windows CPU fallback 环境；
- Mac 结果只能补充跨平台纯逻辑检查，不能替代商业交付验证。
